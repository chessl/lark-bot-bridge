# 飞书群聊 Mention 与发送者身份能力边界

> 调研时间：2026-08-24。范围只覆盖 issue #33 所需的协议、SDK 与当前 bridge 行为。
>
> 证据标签：**文档事实** = 飞书开放平台公开承诺；**源码行为** = 一方 SDK 或本仓库当前实现；**待探针** = 文档和源码仍不能证明的真实租户行为。

## 结论

可以可靠做到两件事：

1. 在 `im.message.receive_v1` 事件中用 `sender.sender_type` 区分人和 Bot；缺失时必须保留为 unknown，不能反推为人。事件文档的枚举是 `user | bot`，而消息 REST 返回体使用 `user | app | anonymous | unknown`，所以跨事件/REST 的统一层应同时接受 `bot` 和 `app`。[飞书接收消息事件](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive?lang=en-US) [飞书获取消息](https://open.feishu.cn/document/server-docs/im-v1/message/get?lang=en-US)
2. 用同一应用上下文收到的 mention `open_id` 生成 text/Post/CardKit 的真实 `<at>`，并通过 IM create 或 reply 发送；但 **“另一 Bot 的 mention ID 能否稳定复用并触发它的事件”不能只靠文档判定**。必须在真实租户验证 ID 形态、Card mention 事件和通知行为。[飞书用户身份](https://open.feishu.cn/document/home/user-identity-introduction/introduction) [飞书接收消息事件](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive?lang=en-US) [飞书发送消息内容](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/create_json?lang=en-US)

Bot-to-Bot 投递不是默认能力。只接收“用户 @ Bot”的旧权限不会投递其他 Bot 的消息；至少需要 `im:message.group_at_msg.include_bot:readonly`（只收用户/Bot 对本 Bot 的 @）或 `im:message.group_msg.include_bot:read`（收群内用户/Bot 消息；不含本 Bot 自己发出的消息）。平台还列出 `im:message.group_bot_msg:readonly`。[飞书接收消息事件](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive?lang=en-US)

当前 bridge 已保留 raw event、兼容 `app | bot`、按 `threadId` 回复并在话题事件缺 ID 时尝试回查；但还没有完成可靠跨 Bot mention：`@larksuite/channel@0.5.0` 的公开 `MentionInfo` 丢掉 raw `mentioned_type`，其 `isBot` 只识别“被 @ 的是否是本 Bot”，当前 bridge 又直接消费这个字段；同时 SDK 的 `mentions` 选项只自动注入 text 和 markdown→Post，不会改写 raw Post 或 CardKit JSON。[当前依赖](https://github.com/chessl/lark-bot-bridge/blob/872aae3/package.json#L48-L51) [channel mention 归一化](https://github.com/larksuite/channel-sdk-node/blob/d41b81c350d4c4df27d26d94dcd7b24bc96cef8a/src/normalize/mentions.ts) [bridge mention 合并](https://github.com/chessl/lark-bot-bridge/blob/872aae3/src/bot/channel.ts#L1283-L1299) [channel outbound sender](https://github.com/larksuite/channel-sdk-node/blob/d41b81c350d4c4df27d26d94dcd7b24bc96cef8a/src/outbound/sender.ts)

## 当前代码的尖锐边界

1. **发送者类型可用，但代码在绕过新版标准字段。** `@larksuite/channel@0.5.0` 已公开 `senderType/senderIsBot`，bridge 仍从 `msg.raw` 读取；行为正确但增加了对 raw 载荷的耦合。[channel types](https://github.com/larksuite/channel-sdk-node/blob/d41b81c350d4c4df27d26d94dcd7b24bc96cef8a/src/types.ts) [bridge](https://github.com/chessl/lark-bot-bridge/blob/872aae3/src/bot/channel.ts#L1263-L1274)
2. **`MentionInfo.isBot` 不能回答“这个 mention 是另一个 Bot 吗”。** 当前提取器只比较 mention open_id 与本 Bot open_id；官方 raw `mentioned_type` 才是目标类型证据。[mentions source](https://github.com/larksuite/channel-sdk-node/blob/d41b81c350d4c4df27d26d94dcd7b24bc96cef8a/src/normalize/mentions.ts) [接收事件](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive?lang=en-US)
3. **按名字找 Bot 不是可靠协议。** 官方 chat-members API明确过滤 Bot；channel 的 `getChatBots()` 调用未公开生成类型的 `/members/bots` endpoint，并把 `bot_id` 标作 open_id。这个 endpoint、权限及 ID 可发送性都应视为源码行为并做租户探针，而不是公开保证。[官方成员列表](https://open.feishu.cn/document/server-docs/group/chat-member/get?lang=en-US) [channel getChatBots](https://github.com/larksuite/channel-sdk-node/blob/d41b81c350d4c4df27d26d94dcd7b24bc96cef8a/src/channel.ts)
4. **当前 OMP 回复不自动 mention 任何目标。** OMP 首选 CardKit，降级为 raw Post；两条路径都没有传结构化 `mentions`，而 channel 也不会替 raw Post/Card 改写。[reply controller](https://github.com/chessl/lark-bot-bridge/blob/872aae3/src/bot/omp-reply-controller.ts) [renderer](https://github.com/chessl/lark-bot-bridge/blob/872aae3/src/card/omp-reply-renderer.ts) [sender](https://github.com/larksuite/channel-sdk-node/blob/d41b81c350d4c4df27d26d94dcd7b24bc96cef8a/src/outbound/sender.ts)
5. **include-bot scope 不能靠运行时代码补救。** 平台在投递前按权限过滤；当前 scope 检查只认识用户全群旧 scope。没有 include-bot 时只能降级为真人触发或让真人转发。[接收事件](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive?lang=en-US) [app-scope](https://github.com/chessl/lark-bot-bridge/blob/872aae3/src/bot/app-scope.ts)

## 最小降级顺序

1. `senderType` 缺失：标为 unknown，按不可信外部输入处理；不将其归为真人。[channel types](https://github.com/larksuite/channel-sdk-node/blob/d41b81c350d4c4df27d26d94dcd7b24bc96cef8a/src/types.ts)
2. 没有 include-bot scope：关闭跨 Bot 自动接力，只保留真人 @；这是平台投递边界，不做轮询式伪补偿。[接收事件](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive?lang=en-US)
3. 目标 mention ID 不确定：只复用本应用 raw event 实际收到的 open_id；否则纯文本名字并要求真人确认，不按名字或跨应用 open_id 猜测。[用户身份](https://open.feishu.cn/document/home/user-identity-introduction/introduction)
4. CardKit 的 Bot mention 未通过探针：同一 `replyTo/thread` 先发 text 或 markdown→Post mention，再发/更新 Card；不要只把名字画在 Card 上。[发送内容](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/create_json?lang=en-US) [Card 富文本](https://open.feishu.cn/document/feishu-cards/card-components/content-components/rich-text?lang=en-US)
5. raw Post/Card 组装失败：退到 text `<at user_id="…">`；若 ID 也不可用，再退纯文本，不制造“看起来像 @”的假通知。[发送内容](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/create_json?lang=en-US)
6. topic `thread_id` 回查失败：仍 replyTo 触发消息但不强制创建 thread，记录位置降级；避免把缺失信号解释为“新开话题”。[reply](https://open.feishu.cn/document/server-docs/im-v1/message/reply?lang=en-US) [bridge fallback](https://github.com/chessl/lark-bot-bridge/blob/872aae3/src/bot/thread-id.ts#L19-L36)

## 必须做的真实租户探针

使用两个独立应用 Bot A/B、一个真人、一个普通群和一个话题群；保存双方 raw event 与 IM API 返回体，逐项验证：

1. B 分别用 text、Post `at`、CardKit `<at>` @ A；A 授权前后对比 `im:message.group_at_msg.include_bot:readonly` 的事件投递，确认缺权限确实静默以及授权生效是否需重连。[权限依据](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive?lang=en-US)

3. 将 A 从 B 事件取得的 A/B Bot mention ID 分别回用于 B 的 text/Post/CardKit 消息，确认 API 是否接受、客户端是否产生真实 @ 提醒、A 是否收到 mention 事件；不能只看渲染出的蓝色名字。[发送内容](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/create_json?lang=en-US) [Card 富文本](https://open.feishu.cn/document/feishu-cards/card-components/content-components/rich-text?lang=en-US)

## 建议决策

- 把 **raw `mentioned_type` + 本应用事件 ID** 定为 mention 目标事实源；不要把 `MentionInfo.isBot` 或名字解析当身份依据。
- 把 `im:message.group_at_msg.include_bot:readonly` 定为 Bot 协作最小权限；只有确实要监听未 @ 的 Bot 消息时才申请更宽的 `im:message.group_msg.include_bot:read`。
- 跨 Bot 接力在探针通过前采用“同线程 text/Post mention + Card 内容”的双消息降级；探针通过后再决定是否只保留 CardKit mention。
- 保留现有 `replyTo + threadId` 位置策略和 `message.get` 回查；位置未知时不主动开 thread。
